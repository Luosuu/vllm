## Codebase Patterns
- vLLM profiling uses `--profiler-config` JSON with keys: profiler, proton_profiler_dir, proton_context, proton_data, proton_hook
- SGLang profiling uses `python -m sglang.profiler` with `--no-cpu --no-gpu --proton` flags and `--proton-context`, `--proton-data`, `--proton-hook` args
- SGLang bench_serving uses `--random-input`/`--random-output` (no `-len` suffix); vLLM uses `--random-input-len`/`--random-output-len`
- SGLang server with CUDA graphs + Proton: `SGLANG_PROTON_CUDA_GRAPH=1 python -m sglang.launch_server --model-path <model> --port 30000`
- vLLM server with CUDA graphs + Proton: `vllm serve <model> --port 8000 --profiler-config '{...}'` (early-start pattern handles Proton+CUDA graph)
- vLLM environment: ~/vllm/.venv, SGLang environment: ~/sglang/.venv
- proton-viewer command: `proton-viewer -m time/ns <file.hatchet>`
- REPO_ROOT for comparison scripts is 3 levels up from SCRIPT_DIR (comparison/ -> profiling/ -> scripts/ -> repo)
- SGLang's _ProfilerProton.stop() was patched to call finalize() for non-persistent sessions — verify persistent sessions are NOT finalized on /stop_profile
- SGLang --num-steps controls forward steps (not requests); 100 prompts × 256 output tokens ≈ 25,600 decode steps
- CUPTI error 39 root cause: CUDA only allows ONE CUPTI subscriber. Three things compete: (1) CUDA graph capture, (2) torch.profiler.ProfilerActivity.CUDA, (3) Proton's CUPTI backend
- SGLang fix: SGLANG_PROTON_CUDA_GRAPH=1 creates persistent Proton session BEFORE graph capture → Proton owns CUPTI → graphs capture fine → session deactivate()/activate() for profiling window
- vLLM fix: early-start pattern (start_and_deactivate() before capture_model()) → same approach
- SGLang profiler client MUST use --no-cpu --no-gpu --proton to prevent torch.profiler from also subscribing to CUPTI
- vLLM /start_profile + /stop_profile may accumulate into one .hatchet file — may need server restart per rate
- Kernel categorization logic lives in scripts/profiling/comparison/analyze_kernels.py
- v1 asymmetries fixed in v2: (1) CUDA graphs now ON for both (was ON/OFF), (2) per-rate sessions for both, (3) SGLang --num-steps=30000 (was 100), (4) higher rates: 4,16,32,inf (was 1,4)
- Per-rate server restart pattern: stop_server → start_server(rate_dir) → wait_for_server → warmup → profile; ensures each rate gets its own .hatchet file
- Warmup should run AFTER server restart but BEFORE /start_profile to warm caches without polluting profile data

## 2026-03-16 - US-001

- Key design: server restarted per rate to guarantee separate .hatchet files (v1 accumulated into one file)
- **Learnings for future iterations:**
  - Per-rate server restart is necessary because vLLM /start_profile + /stop_profile may accumulate into a single .hatchet — restarting the server per rate guarantees isolation
  - Warmup must happen after server start but before /start_profile — this warms CUDA caches and JIT without polluting the profile
  - `sleep 2` after server kill helps release the port before restarting
  - CUDA graphs are the default for vLLM — no flag needed (just avoid --enforce-eager)
  - The v1 script at vllm_online.sh is a good reference for patterns; v2 adds per-rate restart, warmup, and configurable rates
