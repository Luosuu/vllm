## Codebase Patterns
- **nano-vllm profiler**: code is at `submodules/nano-vllm/nanovllm/profiler.py`, tests at `submodules/nano-vllm/tests/test_profiler.py`
- **nano-vllm test isolation**: import profiler module directly via `importlib.util.spec_from_file_location()` to avoid triggering `nanovllm/__init__.py` → transformers import chain
- **nano-vllm triton mock**: use `types.ModuleType("triton")` with `__spec__` set, not plain `MagicMock()`, or transformers import introspection crashes
- **nano-vllm engine test isolation**: register `nanovllm` and `nanovllm.engine` as namespace packages (with `__path__`), mock `xxhash`, stub `nanovllm.config` to avoid `transformers.AutoConfig` import chain
- **scope annotation pattern**: split `method()` into `method()` (wraps with proton_scope) + `_method_impl()` (original logic) to avoid deep indentation
- **nano-vllm submodule commits**: commit inside `submodules/nano-vllm/` first, then commit submodule ref in parent repo
- Profiler code lives in `vllm/profiler/wrapper.py` (implementations) and `vllm/config/profiler.py` (config)
- `ProfilerKind` is a `Literal` type in `vllm/config/profiler.py`
- `WorkerProfiler` is the abstract base class; subclasses implement `_start()`, `_stop()`, and `annotate_context_manager()`
- Profiler creation is inline in GPU worker's `profile()` method (no separate factory function)
- GPU worker uses lazy profiler init; CPU/XPU workers use eager init
- `triton.profiler` is the import path for Proton (`import triton.profiler as proton`)
- Proton API: `proton.start(name, hook)` returns session_id, `proton.finalize(session=id)`, `proton.scope(name)` is a context manager
- `proton.start()` accepts: name, context ("shadow"/"python"), data ("tree"/"trace"), backend ("cupti"/"roctracer"/"instrumentation"/None), mode (string), hook ("triton"/None)
- ProtonProfilerWrapper takes `output_dir` and `local_rank` params (not `worker_name` like Torch)
- `torch_profiler_dir` is for torch profiler only; `proton_profiler_dir` is for proton profiler (fully separated)
- Proton validation lives in `_validate_proton_fields()` helper called from main validator
- Periodic flushing mode detected by checking `proton_mode.startswith("periodic_flushing")` — mode string may be "periodic_flushing" or "periodic_flushing:format=hatchet_msgpack"
- In periodic mode: `_create_session()` on first `_start()`, then `activate()`/`deactivate(flushing=True)` on subsequent cycles; `finalize()` only on `shutdown()`
- In non-periodic mode: `_create_session()` + `finalize()` on every start/stop cycle (unchanged from before)
- Start/stop profile API is pass-through: LLM → LLMEngine → EngineCore → Worker.profile() — only worker has profiler type branching
- GPU worker has TWO places where profiler type matters: (1) early validation in `__init__` and (2) lazy instantiation in `profile()` — both must be kept in sync
- ProtonProfilerWrapper.get_status() returns a plain dict — use this for API endpoint responses
- New RPC methods need 5 layers: Worker → Executor → EngineCore → CoreClient (base + InprocClient + SyncMPClient + AsyncMPClient) → AsyncLLM → EngineClient protocol
- Environment managed by `uv`; activate with `. .venv/bin/activate`
- For TP>1, use `--tensor-parallel-size 2` with `vllm serve`; each rank produces its own output file
- Proton source and docs at `submodules/triton/third_party/proton`
- **CRITICAL BUG**: Proton C++ `setPeriodicFlushingMode()` in `GPUProfiler.cpp:178` has a missing `return` — when mode is just "periodic_flushing" (no `:format=...` suffix), it falls through to access `modeAndOptions[1]` causing a segfault. Fixed by adding `return` after the default format assignment.
- Periodic flushing design: the current phase is NEVER flushed during `deactivate()` — only _previous_ phases are flushed. So phase N's output file only appears after phase N+1's deactivate. First output file appears after second start/stop cycle.
